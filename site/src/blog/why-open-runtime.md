为什么要自研一个开源执行器 runtime

> CodeFlow 的服务端负责调度与治理，真正"干活"的是执行器：它接收任务包、驱动 CLI、逐步执行 SDLC。这个组件我们决定自己写，并且开源。本文记录决策过程。

## 起点问题：命脉在别人手里

在自研 runtime 之前，执行通道是一个闭源的 npm 包：没有源码、没有独立许可证说明、版本与自动更新由上游服务端控制。这意味着三件事：

1. **无法审计**。客户——尤其金融与央国企——会问"执行侧到底跑了什么"，我们答不全；
2. **无法自主**。执行器创建被硬性锁定在特定 CLI 通道上，企业已采购的其他 Agent 客户端接不进来；
3. **无法谈判**。服务端其实已经预留了多种 client kind 与 provider 映射，但没有任何开源 runtime 能消费它们。

## 协议是公开的，所以自研可行

调度器与执行器之间只有 WebSocket 协议帧契约：心跳与能力声明、任务包下载（sha256 校验）、SDLC 逐步执行、澄清会话、交付备注上报——七帧闭环。协议文档与服务端源码完全公开。

这是自研可行性的根基：**要复刻的不是黑盒行为，而是一份白纸黑字的契约。**

## 我们做了什么

- **Provider 适配层**：把"平台语义（SDLC 步骤、门禁）"翻译成"CLI 调用"。首批六种客户端开箱即用：Claude Code、Codex CLI、Cursor CLI、Gemini CLI、Qoder CLI、Qoder CLI CN；
- **模型自由**：任意 Anthropic 兼容端点，`ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN` 即接。账单走客户自己的 API key，不锁定在任何模型的 Credits 体系里；
- **生产级韧性**：本地 SQLite 持久化运行状态，断线指数退避、上线自动唤醒，崩溃恢复不丢产物；同一 executorId 单实例约束（后来者顶掉先来者）；
- **零依赖**：纯标准库实现（Python ≥ 3.11），独立进程，只通过协议帧与平台交互，不引用平台代码。

## 做完之后

平台（MIT）+ 开源 runtime = 全链路可自部署、可审计。客户问"数据不出域能不能用"，答案是能。

更重要的是生态位：服务端预留的三类 client kind 有了第一个开源实现，后续新 provider 按同一适配层扩展——执行侧不再是某一家 CLI 的专属通道。
