一条缺陷工单，52 分钟后变成一个修复分支

> 本文是对一次真实交付的完整记录：真实禅道 18.10、真实模型通道、真实 git 仓库。执行全部交给平台与数字员工，人只做需求澄清与验收。

## 起点：一条普通的缺陷单

禅道里建了一条 bug：「记住我勾选后刷新页面，勾选状态丢失」，关联着前一天刚交付的需求「会员登录页新增记住我功能」。

这条 bug 没有被人工转录进任何内部系统——CodeFlow 绑定产品后自动把它拉进平台，生成工单，等待指派。

## 派发：先失败，后成功

指派给数字员工后，第一次派发因为执行器配置问题失败了。这不是被掩盖的插曲：失败留痕、attempt 递增，修复配置后重新指派，第二次派发受理成功。

**失败不静默，是我们对执行侧的基本要求。** 后面会再看到一次。

## 执行：数字员工做了什么

派发受理后，执行器下载任务包（sha256 校验），按 SDLC 模板逐步执行：

1. **澄清**：数字员工经平台 MCP 实时读取工单，确认复现路径与验收口径；
2. **定位**：自主定位到真实 git 仓库，理解现有登录页结构；
3. **编码**：自建分支 `feat/10007-remember-me`，修改登录页（约 80 行）、新建 RememberMeService、补充 3 个测试类；
4. **验证与交接**：测试通过后推送分支，生成交付报告。

全程没有人工参与编码。人出现在两个地方：一开始澄清了复现路径，最后验收了分支与报告。

## 回写：闭环合上

工单流转到「已关闭」。数字员工的修复报告经备注通道回写到禅道那条 bug 的描述里，带幂等 marker——重复上报不会产生重复备注。禅道侧显示的编辑者是集成账号。

至此，这条缺陷从建单到修复分支推送、再到源头回写，全程在一个闭环里完成，编码部分实测约 52 分钟。

## 这次记录说明什么

**交付不是纸面文档。** 数字员工的产出物是一段可以 checkout、可以跑测试、可以直接 review 的分支——而不是一份"我做了什么"的汇报。

**失败处理是产品能力的一部分。** 执行器配置问题导致的失败被如实记录；另一轮测试里，一个错误模型名的请求在 40 秒内被如实标记 FAILED 并交回真人。诚实上报比虚假的"全部成功"更有价值。

**回写让闭环值得信任。** 交付结论回到源头工单平台，跟着缺陷走，而不是留在另一个系统里等人去查。
