mock 只能验证管道，真模型才能验证产品

> 第一轮真实模型测试结束后的复盘。结论写在标题里，过程值得展开。

## 测试策略的分野

开发期我们跑了两套测试：一套 mock（假模型、固定输出，验证管道与状态机），一套真实模型（真 CLI、真 token、真失败）。

mock 全绿是必要条件，但它验证的只是"管道通"：派发能到、结果能回、状态能流转。它回答不了产品问题——数字员工面对一个模糊需求时表现如何？模型抽风时系统行为是否可预期？

所以第一轮核心测试全部用真实模型跑：真服务端、真执行器、真 git 仓库。

## 实测记录

- **工单创建 → 派发受理**：8 秒内收到 `dispatch.accepted`；
- **四步 SDLC 全流程**：12 分钟跑完，交付可运行代码 + 19 个单元测试全部通过 + 全套文档；
- **坏模型名**：40 秒内如实 FAILED 上报——不是重试到天荒地老，也不是假装成功；
- **进程保护**：20 秒超时杀树，daemon 存活，下一个任务不受影响；
- **双角色小队**：两个数字员工自动接棒，全链路没有人工重新指派。

## 真实运行暴露了什么

三个高优先级缺陷，全部是 mock 测试不可能发现的：

1. **语义级误判**：模型输出格式与解析器的边界假设冲突——mock 的固定输出永远踩不到这条路径；
2. **时序假设错误**：真实 LLM 的响应时长分布远比 stub 宽，一个"不可能超时"的分支被真实命中；
3. **失败路径缺失**：mock 不会产生"模型说了但说得不对"这种最常见也最难缠的失败形态。

每一个都在真实运行中复现、修复、复测。

## 复盘结论

**mock 的价值是让真实测试值得做**：它先把管道问题清场，让真实测试的每一次失败都指向真问题。反过来，只做 mock 的上线是赌博——产品的失败形态只存在于真实运行里。

这套"mock 清场 + 真模型验证产品"的打法后来成了我们的固定流程：每一轮功能收口，都必须过一次真实模型的全链路。
