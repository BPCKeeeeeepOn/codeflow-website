# 教程 03 · 告警引擎设计（指纹状态机 / 双表账本 / 对账调度 / 通知节奏）

> 目标：说清"为什么一条规则能对 100 台主机只产生 1 个事件、恢复不误报、重启不丢事件、
> 通知不轰炸"，以及每一处的代码位置。**这一篇是面试最容易被追问的部分，建议吃透。**
> 代码：`app/engine/state.py`（纯逻辑，可单测）、`app/engine/core.py`（Worker/消费者/广播）。

## 1. 指纹：把"同一条告警"定义清楚

```python
# app/engine/state.py
def fingerprint(rule_id, labels, severity, query) -> str:
    sorted_labels = ";".join(f"{k}={labels[k]}" for k in sorted(labels))
    return hashlib.md5(f"{rule_id}|{sorted_labels}|{severity}|{query}".encode()).hexdigest()
```

- `labels` **必须排序**后再拼，否则字段顺序不同会被算成两条告警；
- `labels` 至少含 `host` 与 `metric` → 一条规则 × 100 台主机 = 100 个互不干扰的指纹；
- `query` 里塞了 `scope:metric:algorithm:expr:queries` → **改表达式/换算法 = 换指纹 = 新事件**，
  老事件按"指纹消失"走恢复。这个设计来自夜莺 `process.go:797`。

## 2. cur / his 双表：账本 vs 状态

| 表 | 语义 | 写规则 |
|---|---|---|
| `alert_cur_events` | **当前活跃状态**（一指纹一行，PK=hash） | 首次触发 upsert；恢复时**删除** |
| `alert_his_events` | **追加账本**（只 insert） | 首次触发、真发了通知、恢复各写一行 |

为什么这么分：查询"现在有哪些告警"要快（一张小表），审计"这个告警历史上怎么变的"要全（账本只追加）。
`is_recovered` 标记恢复行，`recover_time` 记录时刻。

关键取舍（**踩过的坑**）：更新事件若也写账本，100 台主机 × 15s 会让他的表每天涨几十万行 ——
所以账本只在"有意义的变化"时追加（`is_new or notified or is_recovered`）。

## 3. 状态机四态

```python
out = sm.process(anomalies, now)     # anomalies: [(labels, value)]
```

| 情况 | 行为 |
|---|---|
| 新指纹 | 建 `FireState` → 产出 **firing** 事件（deepcopy 入队） |
| 已在 fires | 更新 `trigger_value/trigger_time` → 产出 **updated** 事件 |
| 本轮缺失 + 未过留观 | 什么都不做（`recover_duration_s` 留观） |
| 本轮缺失 + 过留观 | 从 fires 移除 → 产出 **recovered** 事件 |
| `for_duration_s > 0` | 先落 `pendings`，持续够时长才真正触发 |

> ⚠️ **updated 必须入队**（D9 实测修正的缺陷）：早期的实现只改内存状态、不入队，
> 导致消费端的通知节奏判定（`should_notify`）**永远不会被再次调用** —— FR-C5 的
> "repeat_step 到时重发"在真实链路里从未发生。D2 当年只单测了纯函数，没测链路是否调到它。
> 你在做类似设计时记住这条：**"状态变了"和"有人需要知道"是两件事，别把它们绑在同一层。**

## 4. 入队前必须 deepcopy

```python
self.fires[h] = FireState(ev=ev, ...)
out.append(copy.deepcopy(ev))   # ⚠️ 引用入队会被后续评估原地改写
```

夜莺注释里明确写过这个坑：队列里的对象被下一轮评估原地改成"恢复事件"，历史全乱。
Python 里也不要用同一个 dict/对象入队。

## 5. 对账调度：为什么不是"一条规则一个 cron job"

```python
async def reconcile():                       # 每 9s 一次
    rules = 启用规则
    for rid in expected - set(workers): 起 worker
    for rid in set(workers) - expected: 停 worker
    for r in rules:                      # 配置变更 → 重建 worker（比对关键字段）
        if 关键字段变了: stop + 新建
```

好处：规则 CRUD 只影响相关 worker（**≤15s 内生效**，验收项）；坏规则不会影响别人；
不用为每条规则维护 cron 表达式（`eval_interval_s` 或 `cron_pattern` 由 worker 自己算下次时间）。
`APScheduler` 只用来托管**巡检**的 cron，`max_instances=1` 防堆积。

自检：`GET /api/ops/dev/engine-state` 能看到对账心跳（`age_s`）、worker 清单与每个 worker 的
`fires` 数、事件队列深度、SSE 订阅数。**排障第一站**——"规则改了没生效"和"评估没命中"能一眼分开。

## 6. 通知节奏（三参数 + 台账）

```python
should_notify(st, repeat_step_min, max_number, notify_recovered, ev_is_recovered)
```

| 参数 | 语义 |
|---|---|
| `notify_repeat_step_min` | 0 = 只发一次；N = 每隔 N 分钟重发 |
| `notify_max_number` | 最多发多少条（`notify_count = 1 + 已发数`，封顶判定用的是 `>`） |
| `notify_recovered` | 恢复是否通知 |
| `recover_duration_s` | 恢复留观：指标回落要持续这么久才算真恢复 |

每条发送（成功/失败）都写 `notification_records`（渠道/目标/状态/错误）——
"为什么没收到"一查便知。渠道走 apprise（见教程 10），平台只保留业务语义。

## 7. 两级静默

| mute_type | 语义 | 实现要点 |
|---|---|---|
| 0 | **MutedAll**：事件不产生 | 除丢弃外，还要把指纹从状态机 `fires` 里**摘掉**；否则静默解除后该指纹一直在 fires 里走 update 分支，永远不再重新触发 |
| 1 | **NotifyOnly**：事件照常落库，跳过通知 | 台账里能查到"被静默期间发生过"，只是没打扰人 |

周期时段（`periodic_mutes`，如每日 02:00-03:00 备份窗口）+ TagFilter（`== / != / =~ / in`）都支持。

## 8. 一个完整例子（照着数一遍）

规则：`cpu.percent > 85`，`eval_interval_s=15`，`recover_duration_s=60`，`notify_repeat_step_min=30`，`max_number=5`。

```
T0    第 1 台主机 CPU 冲到 92 → 新指纹 → firing → 落 cur + his → 通知 1 条 → SSE firing
T+15  仍 92 → updated 事件 → 队列里走一遍 should_notify：距上次 15s < 30min → 不发；SSE updated
T+30  仍 92 → updated → 还不够 30min → 不发
T+35  指标回落到 40 → 本轮指纹消失 → 留观开始
T+95  留观满 60s → recovered → 删 cur、写 his(recovered) → 按 notify_recovered 决定是否通知
```

想验证：`pytest tests/test_d2_engine.py -q`（触发/更新/留观恢复/重启回放四态都有单测）。

## 9. 边界与已知取舍

- **V1 不执行命令**：平台只判定 + 审计 + 给出待执行命令（护栏见教程 08）；
- 恢复判定基于"本轮评估未见该指纹"，因此**评估异常**时有过一次专门处理
  （Prom 数据源不可达 → 跳过本轮 `process`，避免把"查不到"当"已恢复"）；
- 队列积压保护：队深 > 50 时**AI 摘要让路**（不阻塞通知），见教程 05；
- his 表长期增长需要清理策略（V1 未做自动清理，建议按 `trigger_time` 分区/归档）。
