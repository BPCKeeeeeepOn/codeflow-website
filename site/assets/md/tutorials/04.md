# 教程 04 · 异常检测与规则调优

> 目标：三种算法怎么选、窗口/持续时长/生效时段怎么配、试运行怎么用、
> 以及"为什么我的规则不触发"的排查顺序。
> 代码：`app/engine/detect.py`、`app/engine/core.py: _eval_once`、`app/models/alert.py`。

## 1. 三种算法

| algorithm | 实现 | 适用 | 不适用 |
|---|---|---|---|
| `threshold` | `op value` 比较每个点 | 有明确阈值的**可用性**指标（磁盘水位、CPU 打满、探活失败） | 波动大、阈值难定的指标 |
| `3sigma` | 窗口内均值 ±3σ | 平稳基线上的**尖峰/阶跃**（QPS、延迟） | 强周期指标（白天高晚上低 → 会被误判） |
| `isolation_forest` | sklearn `IsolationForest(n_estimators=50, contamination=0.05)` | 多维/无分布假设的离群 | 样本 < 20 个点（拟合没意义） |

**3sigma 的硬条件**（代码里明确写了）：窗口内 **≥5 个点**且 σ≠0，否则直接返回空
（不硬凑结论）。isolation_forest 走同一套"异常点 → 指纹 → 事件"管线，
指纹里带 `algorithm`，所以**换算法 = 新事件**，老事件按恢复处理。

> 演示技巧：同一条曲线配两条规则（阈值 vs 3σ），故障注入时对比两者触发时机，
> 能直观讲清"自适应检测 vs 静态阈值"的差异。

## 2. threshold 的语义细节（最容易踩）

`threshold` 是对**窗口内每个点**独立判定，命中就产出一个异常点：

```python
return [({}, v) for _, v in points if fn(v, thr)]
```

看起来简单，但配合"指纹"就有个反直觉的后果：**窗口里只要有一个点超阈，规则就会告警**。
所以：

- 想要"持续超阈才告警" → 用 `for_duration_s`（先落 `pendings`，持续够时长才触发）；
- 想要"回落就恢复、别抖" → 用 `recover_duration_s`（留观）；
- 排除单点毛刺 → 把 `window_s` 调小（1-2 个采集周期），或改用 `3sigma`。

**写测试时的坑**（我们在 D2 踩过）：想让规则触发，得让窗口内**所有**点都超阈，
或者清空环形窗口只留一个超阈点——不然测试会莫名其妙不触发。

## 3. 参数怎么配（给三组可直接用的）

| 场景 | window_s | eval_interval_s | for_duration_s | recover_duration_s | 备注 |
|---|---|---|---|---|---|
| 磁盘水位（慢变量） | 600 | 60 | 0 | 300 | 别设太灵敏，磁盘告警半小时一次就够 |
| CPU 打满（快变量） | 300 | 15 | 60 | 120 | 打满持续 1 分钟才算，避免编译/备份误报 |
| 探活失败（可用性） | — | 15 | 0 | 60 | `scope=probe`，取值 `down→1/up→0`，expr `>0` |

`cron_pattern` 与 `eval_interval_s` 二选一：填了 cron 就按 cron 算下次评估时刻
（如 `*/5 * * * *`），非法表达式会**回落固定间隔**并留一条 warning（不影响告警链路）。

## 4. 生效时段（避免半夜叫你起床）

`effective_time` 是段列表，每段 `{days:[0-6], start:"09:00", end:"18:00"}`（UTC；空 = 全天）。
段外**不评估**（不是"评估了不通知"）——所以段外的指纹会走恢复，这是有意的：
避免"只在工作时间告警"的规则在非工作时间一直挂着活跃事件。

## 5. 试运行（不落事件）

```bash
POST /api/ops/alert-rules/{id}/test   {"window": "30m"}
```

返回窗口内命中的点与异常计数，**不写 cur/his、不发通知**。改表达式前先试运行，
是"避免误伤生产告警"的最省事办法。UI 入口在「告警规则 → 编辑 → 试运行」。

## 6. "规则不触发"排查顺序

1. `GET /api/ops/dev/engine-state` → 看对账心跳与 worker 是否 `alive`、`fires` 数
   （**对账没跑** vs **评估没命中**，这一步就分开了）；
2. 规则是否 `disabled`、是否在 `effective_time` 段外；
3. 数据有没有到平台：`GET /api/ops/metrics/query?ident=<ident>&metric=cpu.percent&minutes=30`
   （空 = 采集/上报问题，不是规则问题）；
4. 表达式与算法：`>85` 别写成 `>=85` 之外的变体；`3sigma` 要 ≥5 个点；
5. 静默：`GET /api/ops/alert-mutes` 是否命中（MutedAll 连事件都不产生）；
6. 队列积压：`engine-state.event_queue_size` 很大 → 消费者被拖住了（见教程 05/12）。

## 7. 复盘：为什么我们没做"告警风暴治理"

需求里明确列了 V1 不做企业级风暴治理。当前机制实际提供的最小防护是：
指纹去重（同因反复触发不重复建事件）+ 收敛（多告警合成一个 incident）+
通知封顶（`notify_max_number`）+ 摘要让路（队深 >50 时跳过 LLM）。
更强的聚合/降噪（如同源抑制、依赖拓扑抑制）留 V2。
