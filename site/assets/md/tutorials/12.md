# 教程 12 · 运维与排障手册

> 目标：线上出问题时按图索骥。包含**自检端点、日志、常见故障、性能基线、备份、
> License 行为、以及本产品已知的坑**。

## 1. 第一站：引擎自检

```bash
GET /api/ops/dev/engine-state
```

```json
{
  "reconcile": {"last_at":"...Z","age_s":3.1,"count":15,"consecutive_errors":0,"period_s":9,"healthy":true},
  "workers": [{"rule_id":1,"rule_name":"演示-CPU高负载","disabled":false,"fires":15,"alive":true}],
  "event_queue_size": 0,
  "sse_subscribers": 2
}
```

读法：
| 现象 | 含义 | 处理 |
|---|---|---|
| `healthy:false` / `age_s` 很大 | **对账循环没在跑** → 新建/删除规则都不生效 | 看 ERROR 日志的"对账异常"；重启平台 |
| `workers` 里没有你刚建的规则 | 对账没跑到 / 规则被禁用 | 等 9s 再看；确认 `disabled=false` |
| 某 worker `alive:false` | 该规则 worker 挂了 | 改一下规则关键词段触发重建，或重启 |
| `fires` 数异常大 | 状态机里挂着大量活跃指纹（通常是已被删主机/规则的历史残留） | 见 §5 的孤儿事件清理 |
| `event_queue_size` 持续增大 | **消费端被拖住**（历史故障：AI 摘要阻塞） | 看 §4；队深 >50 会自动跳过摘要让路 |

## 2. 日志

- 默认人读格式；容器/采集场景开 **JSON 日志**：`LOG_JSON=true` → 单行 JSON
  （`ts/level/logger/msg` + 异常栈），filebeat/loki 直接解析；
- 容器看日志：`docker logs -f aiops-platform`；
- `log.exception` 的堆栈一定先看"哪个 task/规则/事件"，别只看最后一行。

## 3. 常见故障对照表

| 症状 | 定位 | 处理 |
|---|---|---|
| 页面空白 | ESM 模块语法错（整个图失败） | `node --check static/js/pages/*.js`；跑 `pytest tests/test_d3_frontend_assets.py` |
| 所有接口 403 且 msg 含 `LICENSE_LOCKED` | License 门禁生效且已锁 | 系统设置页激活；或确认 `LICENSE_ENFORCE=false`（源码交付默认关） |
| AI 功能报 `InvalidTag`（消息可能是空的） | `KEY_STORE_SECRET` 与写入时不一致 | 重新保存模型配置；**不要随意改这个密钥** |
| AI 报 `LLM_QUOTA_EXCEEDED` | 当日用量超限 | 调 `LLM_DAILY_TOKEN_LIMIT`/`DEMO_DAILY_TOKEN_LIMIT`（0=不限）；UTC 次日重置 |
| 时间显示 "-27896 秒前" | 数据库会话时区不是 UTC | 确认连接串带 `SET time_zone='+00:00'` |
| 主机一直 offline | 心跳超 `3×interval`（默认 45s） | 目标机到平台 8848 通不通；Agent 是否活着 |
| 主机名查不到数据 / 诊断说"未注册" | 早期数据把主机名写进了 `host_ident` | `python scripts/repair_demo_data.py --apply` |
| 前端某页报 `HTTP 403` | 角色无权（能力集不含该项） | 用 admin；或确认 `DEMO_CHAT_ENABLED` 等开关 |
| 磁盘涨得快 | `metric_agg` + `alert_his_events` 长期增长 | V1 未做自动清理：`alert_his_events` 按 `trigger_time` 归档删除；`metric_agg` 按保留期清 |
| **升级后界面没变化 / 部分页面空白** | 浏览器缓存了旧 JS（免构建前端模块名固定） | 平台已默认返回 `Cache-Control: no-cache`（每次协商）；从**老版本**升上来时可能残留旧缓存 → **强刷一次**（Cmd/Ctrl+Shift+R）即恢复 |
| **告警中心被同一条告警刷屏（同一秒几十条相同记录）** | 老版本 bug：同一轮评估内同指纹的多个采样点被逐点入队（D9-1） | 升级到含 v1.14 的版本；库里已有重复行按 §3.1 清理 |
| **变更单生成不动 / 提示 `NO_VALIDATED_FIX`** | 建议段只有"描述"没有可执行命令，或与预置验证对不匹配（D9-3 已放宽只读命令） | 看报告 `## VALIDATED FIXES` 段是否写了**反引号命令**；只读取证命令（`curl -v`/`lsof`/`tail`/`df`…）现在可直接进变更单 |
| **只读命令（如 `lsof`/`curl -v`）被要求审批** | 旧版只读白名单不含这些命令（D9-4 已补） | 升级；或把该步改写成白名单内的命令 |
| **`python scripts/repair_demo_data.py` 报 `No module named 'app'`** | 老版本脚本未自加 `sys.path`（D9-5） | 升级后重跑；临时替代：`cd /app && python -c "import runpy;runpy.run_path('scripts/repair_demo_data.py',run_name='__main__')"` |
| **某渠道告警一直收不到 / 通知台账里该渠道 failed 一堆** | 渠道配置错或对端拒绝；连续失败 5 次后平台会**自动熔断该渠道 30 分钟**（冷却期跳过投递、不写台账），冷却到期自动重试 | 修好渠道后点「测试」；成功一次即恢复（`fail_streak` 清零）。想立刻恢复可把渠道禁用再启用 |
| **通知发送把告警链路拖慢/卡住** | 老版本 apprise 投递无超时：对端"连接挂住"（防火墙 DROP/服务假死）会永久占住投递线程 | 已修（URL 追加 `?timeout=10` + 外层 20s 墙钟兜底）；升级到含 D12 的版本 |
| **同一主机同一时刻的指标在库里有多行** | 老版本聚合水位记桶起点，同一分钟反复 INSERT（D9-2） | 升级 + 按 §3.1 去重（实测一次清掉 27,613 行） |
| **证书探针对自签/内网证书显示 `down` / `-1`** | 老版本 `probe_https_cert` 用 `ssl.create_default_context()`（默认校验证书链+主机名），自签/私有 CA/IP 探 CN 的证书永远抛 `SSLCertVerificationError` → 读不到"还剩几天"（过期也显示 -1 而非负数） | 升级 Agent 到含此修复的版本：改为 `CERT_NONE` 取 `binary_form` DER 自解析 notAfter，链校验结论另存 `verify_error` 字段；升级后目标机需重新拉取 `agent_main.py` |
| **seekdb 容器重建后无限重启**：日志反复出现 `Authentication failed with configured ROOT_PASSWORD for an existing data directory. Refusing to reset`（D114，S1） | seekdb 1.4 的 `/root/start.sh` 读的是 **`ROOT_PASSWORD`**，不是 `OB_ROOT_PASSWORD`。旧 compose 只传了 `OB_ROOT_PASSWORD` → 重建已有数据目录时 start.sh 拿**空密码**校验 → 认证失败退出循环。**数据没有损坏**，只是密码环境变量名不对 | ① 用下方命令确认 `.env` 的 `DB_PASSWORD` 就是当初初始化数据目录的密码；② compose 同时传 `ROOT_PASSWORD=${DB_PASSWORD:-}` 与 `OB_ROOT_PASSWORD=${DB_PASSWORD:-}`（新 compose 已修）；③ 动数据卷前先备份：`tar -czf seekdb-data-backup-$(date +%s).tar.gz -C /var/lib/docker/volumes/aiops-demo_seekdb-data _data`。**教训：改 `.env` 里的 `DB_PASSWORD` ≠ 改库密码**——环境变量不会重置已有数据目录的密码，密码必须与首次初始化一致 |

**seekdb 密码校验方法**（不打印密码本身）：

```bash
pw=$(grep '^DB_PASSWORD=' .env | cut -d= -f2-)
docker exec -e PW="$pw" aiops-seekdb sh -c \
  'MYSQL_PWD="$PW" mysql -h127.0.0.1 -P2881 -uroot -N -e "SELECT user,host FROM mysql.user"'
# 输出 user 列表 = 密码正确；ERROR 1045 = 密码与数据目录不一致
```

### 3.1 metric_agg 重复行清理（D9-2 修复后的一次性动作）

先查有多少重复，再决定要不要清：

```sql
SELECT COUNT(*) FROM (SELECT 1 FROM metric_agg GROUP BY ident,metric,granularity,ts HAVING COUNT(*)>1) x;
```

```bash
docker compose --env-file .env -f deploy/docker-compose.yaml exec platform python -c "
import asyncio
from sqlalchemy import text
from app.db.session import SessionLocal
async def main():
    async with SessionLocal() as db:
        r = await db.execute(text('DELETE t1 FROM metric_agg t1 JOIN metric_agg t2 '
            'ON t1.ident=t2.ident AND t1.metric=t2.metric AND t1.granularity=t2.granularity '
            'AND t1.ts=t2.ts AND t1.id > t2.id'))
        await db.commit(); print('删除行数:', r.rowcount)
asyncio.run(main())
"
```

### 3.2 通知链路自测（不依赖飞书/钉钉 token）

想验证"平台到底发不发通知"而不碰真实渠道：宿主机起一个只记录请求的小接收器，
平台侧建一条 **webhook** 渠道指向它（`http://host.docker.internal:<port>/...`），
再点渠道「测试」或注入一次故障 —— 接收器会打出来自 `UA=Apprise` 的真实 HTTP POST 与正文。
（D9 实测即用此法：告警与恢复两条都到达，台账 `status=sent`。）

## 4. 告警通知延迟（我们踩过的最隐蔽的坑）

**现象**：注入故障后，界面要等几分钟才弹告警；`engine-state.event_queue_size` 持续增大。

**根因**（已修）：`consume_one` 里 `await` 了真调 LLM 的 AI 摘要（数秒/条），
100 台主机同时触发 → 消费者被 LLM 串行拖住 → 队列积压上千条 → 通知与 SSE 全被推迟。
**恰好在最需要通知的时候**。

**现在的行为**：摘要丢到后台任务（并发上限 2）；队深 > 50 时直接放弃本轮摘要并打 warning。
**如果你二次开发时要在告警链路上加东西**（写库、调外部 API、发消息），记住这条：
> 热路径只做"必须立刻做"的事；其它一律异步 + 限并发 + 压力下可放弃。

## 5. 数据卫生（脚本）

```bash
cd backend
python scripts/repair_demo_data.py                     # 只报告：host_ident 对齐 / 孤儿事件
python scripts/repair_demo_data.py --apply             # 落库
python scripts/repair_demo_data.py --purge-orphans     # 清理"主机或规则已不存在"的孤儿事件
```

**孤儿事件的危害**：主机的活跃事件不会随主机行一起消失，会一直挂在大盘/告警中心
（我们实测踩过：压测删主机后留下 100 条幽灵告警）。手工改过库、跑过压测、导过数据后都建议跑一次。

### 5.1 清理测试/压测残留（截图、演示、交付前建议跑一次）

```bash
cd backend
python scripts/purge_test_junk.py                      # 默认 dry-run：只报告会删什么
python scripts/purge_test_junk.py --apply              # 真删
python scripts/purge_test_junk.py --keep-inspections 5 --apply   # 多留几条「即时巡检」
```

**它清什么（只匹配明确的测试特征，不做"看着怪就删"）**：

| 目标 | 依据 |
|---|---|
| 超长标题事件（`^x{20,}$`） | `test_d8_api_matrix` 的"超长标题"边界用例造的数据 |
| 标题含 `<img` / `onerror` 的事件 | XSS 转义用例（TC-FE-22）注入的标题 |
| **`alert_cur_events` / `alert_his_events` 里的测试告警** | 边界用例（XSS 串 / `atk-*` / ≥40 字符的边界串）通过**真引擎**触发过告警，用例只清了规则**没清告警** → 留下会出现在告警中心与 AI 问答里的**孤儿告警**（实测：AI 助手会把这些脏规则名列出来并建议排查，说明它确实读到了） |
| 历史的「即时巡检」记录（保留最近 N 条） | 每次 `run-once` 都会建一条同名记录，反复测试会攒出几十条 |

> 判定"边界串"用的是**名字长度 ≥ 40 字符**而不是正则反向引用 —— 实测 SeekDB 不支持
> `^(.)\1{19,}$` 这类回引（匹配不到会**静默漏删**）。合法规则名都很短（`演示-*` 约 10 字符）。

**为什么要清**：发布截图/演示/交付给买家时，第一眼看到 200 个 `x` 的事件卡片很难看；
本项目自己的截图就是这么清完之后拍的。脚本**默认 dry-run**，且删前后各打印一次计数。

## 7. 备份与恢复

| 数据 | 位置 | 备份方式 |
|---|---|---|
| 全部业务数据 | SeekDB（`aiops` 库） | `mysqldump` 兼容；容器卷 `seekdb-data` |

## 8. License 行为（FR-A4）

| 状态 | 触发条件 | 行为 |
|---|---|---|
| `disabled` | `LICENSE_ENFORCE=false`（默认） | 不做任何限制（源码买家开箱即用） |
| `grace` | 强制开 + 无 License + 在宽限期内（`LICENSE_GRACE_DAYS`，默认 14） | 顶部横幅提示"试用中"，功能可用 |
| `valid` | 有效激活码 | 按模块位渲染导航 |
| `locked` | 强制开 + 无有效 License + 宽限期过 | 核心 API 一律 **403 + `LICENSE_LOCKED`**；登录/健康/License/静态资源/install.sh 白名单不受影响 |

激活码 = HMAC 签名（用 `JWT_SECRET`）+ 机器指纹 + 有效期 + 模块位；
校验含**签发时间比对**（把系统时间往回拨也会被拒）。

## 8.5 长任务超时（504）与"疑似数据库不可达"（500）的区别

这两个错误提示**指向完全不同的原因**，别混淆（我们踩过：25s 兜底把正常的长任务当数据库故障杀掉）：

| 现象 | 真实原因 | 处置 |
|---|---|---|
| **504**「长任务执行超时（>Ns），已中止」 | 该接口确实跑得比它的**兜底上限**还久（巡检/诊断/处置执行/外呼探活） | 缩小范围重试：诊断降 `max_steps`、巡检减少主机、检查对端是否可达 |
| **500**「服务端响应超时（疑似数据库不可达…）」 | **非长任务**接口超了 25 秒 → 基本可判定数据库挂了或查询被锁 | 查数据库：`docker pause seekdb` 类问题、慢查询、锁等待；DB 恢复后下一个请求自愈 |

### 429 LLM_QUOTA_EXCEEDED（演示站/平台 token 配额用尽）

报错形如 `演示模式今日 token 已用尽（760070/200000）`。**先看数字是否自洽**：
如果 `used` 远大于 `limit`，或 demo 自己其实没怎么用，说明是**归属口径**问题而非真的用超了。

排查步骤：

```bash
# 1) 看今天到底是谁在消耗（按归属）
docker exec -i <platform容器> python -c "
import asyncio,sys; sys.path.insert(0,'/app')
from app.db.session import SessionLocal; from sqlalchemy import text
async def m():
    async with SessionLocal() as db:
        for r in (await db.execute(text('''SELECT role,purpose,COUNT(*) n,SUM(total_tokens) t
              FROM llm_usage WHERE created_at>=UTC_DATE() GROUP BY role,purpose ORDER BY t DESC'''))).all():
            print(r)
asyncio.run(m())"
```

| 现象 | 原因 | 处置 |
|---|---|---|
| `role=engine` 占大头（`summary`） | **后台引擎**自动生成的告警 AI 摘要 —— 不是任何人"刷"的 | 归 engine 后**不计入 demo 额度**（D21 起）。要省钱应调 `ALERT_AI_SUMMARY_ENABLED=false` 或降低告警量 |
| `role=admin`/`member` 占大头 | 管理员自己的诊断/巡检/测试 | 与 demo 额度无关；受 `LLM_DAILY_TOKEN_LIMIT` 约束 |
| `role=demo` 占大头 | 演示用户真的在刷 | 抬高 `DEMO_DAILY_TOKEN_LIMIT`，或置 0 不限（公开演示站不建议），或关 `DEMO_CHAT_ENABLED` |
| `role` 为空串的大批行 | **D21 迁移前的历史行**，无法追溯归属 | 不追溯（把管理员的账记到 demo 头上语义相反）；跨日后自然消失 |

置 0 = 不限。重置时间为 **UTC 次日 00:00**。

### 长任务清单在哪

代码里是 `backend/app/main.py` 的 `LONG_TASK_ROUTES` 表（正则 → 兜底秒数），
并有**机械守卫测试**保证"凡跑外部动作的接口必须登记"（漏登记测试会失败）。
**排查时若怀疑某接口也是长任务却没登记**，直接跑 `pytest tests/test_d19_exhaustive_variants.py -q`。

| 接口 | 兜底 | 典型耗时 |
|---|---|---|
| `POST /api/ops/inspections/{iid}/run`、`/run-once` | 600s | 20~48s |
| `POST /api/ops/incidents/{iid}/diagnose` | 900s（路由内 840s） | 43~102s |
| `POST /api/ops/runbooks/{rid}/execute`、`/steps/{i}/confirm`、`/generate/{id}` | 300s | 取决于动作 |
| `POST /api/ops/skills/{sid}/check` | 300s | 取决于技能内容 |
| `POST /api/ops/alert-rules/{rid}/test`、`/api/llm-configs/{cfg_id}/test`、`/api/ops/prom-datasources/{did}/{test,scrape-now}` | 120s | 外呼型 |
| `POST /api/ops/notify-channels/{cid}/test` | 60s | 外呼型 |

> 反例（**这不是长任务**）：`POST /api/ops/skills/{sid}/toggle` 只是翻一个布尔位 —— 若它慢，那是数据库问题。
> 守卫测试里有这份"确认无外部工作"的例外白名单，每条都写了依据。

### 巡检/诊断报"任务不存在或已被删除"（404）

传了不存在的 id。**这是修复后的正确行为**——此前传错 id 会**静默跑一次全量巡检**

## 附 A. Agent 运维（D118~D125 新增）

### A1. 远程升级 Agent（无需登机）
主机列表「可升级」→ 点「直接升级」→ 平台下发任务，Agent 下个心跳（≤15s）自动下载、校验、替换、重启。
- **没升上去怎么查**：任务列表（`/api/ops/tasks?kind=self_upgrade`）看状态；`ok=false` 时 note 里有原因
  （`已是这份代码`=指纹一致无需升；`拒绝降级`=平台版本低于本机；`未检测到 systemd/launchd`=裸进程安装需人工执行）；
- **兜底**：主机列表「命令」按钮生成升级命令，人工登机执行；
- **首次接入例外**：新机器仍需在某台机器上执行一次安装命令建立信任通道，此后所有升级都在平台点。

### A2. 主机显示在线却「无指标」黄徽章
说明 Agent 活着（心跳通）但平台没收到任何指标——采集被跳过或配置有误。
排查：① 详情「最近错误」；② Agent 日志 `journalctl -u opsagent -n 50`（Linux）/ `agent.log`（macOS）；
③ 确认安装成功信号（日志里有「首个上报已确认」=平台已接收本机指标，没有则上报链路有问题）。

### A3. 升级 install.sh 的安全与幂等（D125）
- **并发锁**：同一台机器重复执行安装会抢 `~/.opsagent/.install.lock`，抢不到会明确退出——批量装机不会互踩；
- **配置备份**：覆盖前 `probes.json`/`services.json` 备份到 `~/.opsagent.conf-backup-<时间戳>/`，丢了从这里恢复；
- **注册确认**：安装后等 45 秒要看到「注册成功/首个上报已确认」，否则按三步排查（服务是否跑 / 出站能否访问
  平台 `curl -I <平台>/api/health` / 令牌是否有效）；注册成功但服务没跑会被单独点名。

### A4. 新增指标速查（诊断用）
CPU 分解 `cpu.user/system/iowait`、内存 `mem.available_percent/buffers/cached`、`load.5/15`、
磁盘 IO `disk.io.<设备>.read_bps/write_bps/read_iops/write_iops`、inode `disk.inode.<挂载点>.percent`、
网卡 `net.<网卡>.in_bps/out_bps/in_pps/out_pps/errin/errout/dropin/dropout`、
TCP `net.tcp.established/time_wait/listen/close_wait/syn_sent/total`；进程快照含 RSS 与打开文件数（内存 TopN 不再盲区）。
