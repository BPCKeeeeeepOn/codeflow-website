# 教程 05 · AI 根因诊断 Agent 拆解

> 目标：把"AI 诊断"从玄学讲成工程：单 Agent ReAct 循环、只读工具边界、预算五件套、
> 报告的强 schema、三层留痕、以及**为什么它不会编造**。
> 代码：`app/services/rca.py`（循环）、`rca_tools.py`（工具面）、`findings.py`（校验）、
> `prompts.py`（提示词）、`app/routers/incidents.py`（SSE 出口）。

## 1. 一次诊断的全过程

```
点击"一键诊断"
  └─ collect_context()      并行收集：关联告警 / 主机近期指标 / 探活 / 系统信息 / 历史案例卡
  └─ 预写 rca_findings(status=running)   → 前端立刻出"调查中"卡片（不等结果）
  └─ while step < max_steps:
        call_llm(messages, tools=8个只读工具)
        ├─ 无 tool_calls → 结束循环
        └─ 有 tool_calls → 逐个执行（同参去重）→ 结果回灌 messages
  └─ 终态 write_findings → 强 schema 校验（失败重试 ≤2 → failed stub）
  └─ 写回 incident（ai_report_md / root_cause / confidence）
```

SSE 事件（前端逐步渲染）：`session_start / thinking / tool_call / tool_result /
tool_denied / hint / validate_retry / token_count / content / done`（旧的 `diag_start/diag_done`
保留为兼容别名）。

## 2. 只读工具面（8 个，全部只读）

| 工具 | 作用 | 诚实边界 |
|---|---|---|
| `list_hosts` | 主机清单（ident/name/ip/os/状态/活跃告警数） | — |
| `host_info` | 单主机静态信息 + 活跃告警数 + 探活汇总 | — |
| `query_metrics` | 指标窗口 min/max/avg/latest + 尾部序列 | 环形仅保留有限窗口，超窗走聚合 |
| `check_probe` | 探活状态/延迟/证书剩余天数 | — |
| `list_probes` | 全部探活清单 | — |
| `read_log_tail` | 读日志尾部 | **仅平台自身主机**；远程主机返回 NO_DATA（V1 Agent 不上传日志） |
| `get_process_list` | CPU 占用 Top 进程 | **仅平台自身主机** |
| `search_cases` | 历史案例卡检索（向量/文本） | 向量不可用会降级并如实标注 |

设计原则：**能力不足就明说**（"V1 不读远程日志"），让模型在 `not_checked` 里写清楚，
而不是让它推断一个不存在的日志内容。这是"不编造"的第一道防线。

主机参数 `ident` 与主机名**都认**（ident 精确 → name 精确 → 唯一前缀）——
否则"mock-db-01 的 CPU"这种最自然的问法会返回"主机未注册"，看起来像平台坏了。

## 3. 预算五件套（防跑飞，HolmesGPT 生产验证的做法）

| # | 机制 | 实现 |
|---|---|---|
| 1 | `max_steps`（默认 30） | 循环上限，超了强制收敛 |
| 2 | 最后一轮撤工具 | 只留 `write_findings`，逼模型出结论 |
| 3 | 同参数重复调用拒绝 | `name + sorted(params)` 做键，命中即回"已拒绝重复调用" |
| 4 | 单工具输出超限落盘 | 超限写临时文件，只给路径 + 限量预览 |
| 5 | 历史压缩 | 超过阈值用 fast_model 摘要历史（压缩后仍记住曾致溢出的调用） |

外加**循环护栏**：同工具连续 3 次空/错 → 注入"换个方向"提示；5 次 → 强制收尾。
另有 `LLM_CALL_TIMEOUT_S=180`（单次调用）与 `DIAG_DEADLINE_S=900`（整轮），
到点写 stub 而不是无限等。

## 4. 报告的强 schema（这是"可信"的关键）

`findings_md` = YAML frontmatter + 四个必填 H2：

```yaml
agent_id: rca-1
purpose: 诊断演示告警"CPU高负载"的真实根因
status: succeeded            # succeeded|failed|timeout
tools_used: [query_metrics, check_probe]
citations: [step_1, step_3]  # 只能引用真实执行过的 step
self_assessed_strength: moderate   # strong|moderate|weak|inconclusive
confidence: INCONCLUSIVE     # CONFIRMED|LIKELY|INCONCLUSIVE
impact:
  affected: [{entity: "mock-web-01", evidence_token: "cpu.percent=99.9@step_3"}]
  checked_healthy: []
  changed_other_reason: []
  not_checked: ["远程主机进程清单（V1 不可得）"]
---
## Summary / ## Evidence / ## Reasoning / ## What I ruled out
```

校验点（`app/services/findings.py`）：
1. frontmatter 七字段必填、枚举值必须合法；
2. 四个 H2 缺一即失败；
3. `impact` 四个子键必须都出现；
4. **`affected` 每条必须带 `evidence_token`**（引不出证据的不配进"受影响"组）；
5. `citations` 不得为空，且只能引用实际执行过的 step。

校验失败 → 带着**错误清单**重试（最多 2 次）→ 仍失败写 `status=failed` 的 stub。
另外有个务实处理：模型偶发把 `status`/`confidence` 写串、用中文写强度、把 citations 混在正文里
——这些**机械性错位**会被归一化（而不是直接判失败），只有语义问题才让你重来。

**爆炸半径四分类**抄自 HolmesGPT `generic_ask.jinja2` 原文：
`Affected / Checked, healthy / Changed during the window for another reason / Not checked`。
"时间上的吻合不是因果""症状不是根因"这些约束直接写进系统提示词（出处见 `docs/02-调研/`）。

## 5. 提示词结构（8 段，稳定顺序利于 KV cache）

`_IDENTITY → _METHOD（调查方法论）→ _EVIDENCE（证据标准）→ _ANTI_EARLY（反过早收敛）→
_IMPACT（爆炸半径四分类）→ _FIX（修复幻觉防线 + 报告模板）→ _UNTRUSTED（工具输出不可信）→ _CONTRACT`

关键几条（都可追溯到调研笔记原文）：
- "调用工具前先陈述假设；每轮设计**证伪型**查询，不是确认型"；
- "只有穷尽调查后才允许 INCONCLUSIVE"（相反地，也**不允许**用推断补结论）；
- "提修复前必须只读验证"+"没验证过的修复不建议"（落到 `## VALIDATED FIXES` 段）。

## 6. 三层留痕（可回放）

| 表 | 内容 | 用途 |
|---|---|---|
| `incident_thoughts` | 每步的思考文本（按句/按步） | 前端实时"正在想什么" + 事后回放 |
| `execution_steps` | step_index / tool_name / input / output / status / duration_ms | 工具瀑布图 |
| `rca_findings.tool_call_history` | 完整工具调用历史（JSON） | 审计与二次分析 |

`GET /api/ops/incidents/{id}/findings` 一次返回报告 + 三层留痕，前端把 `(step_N)` 渲染成可点击引用。

## 7. 实测表现与边界

- 真实模型（MiniMax）跑一次典型诊断：8 个工具、**15 次工具调用**、约 3 万 token、1-3 分钟；
- 报告的诚实度实测：面对"主机未纳管 + 数据窗口已过期"的场景，它会给出
  `confidence: INCONCLUSIVE` 并说明"缺什么数据"，而**不是**编一个根因；
- 边界：V1 不执行命令（只给待执行命令 + 判定 + 审计）；远程主机的日志/进程不可得；
  历史窗口受环形缓冲限制（超窗走 1m/5m 聚合）。
