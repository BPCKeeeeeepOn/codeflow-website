# 教程 07 · Skills 扩展开发

> 目标：理解 SKILL.md 规范、连接检查（fail-closed）的语义，并**自己写一个能用的技能**。
> 代码：`app/services/skills.py`（注册表/检查/索引）、`app/services/rca.py`（索引注入 + `load_skill`）。

## 1. 为什么用 SKILL.md 而不是把方法论塞进 system prompt

两家独立开源（Aurora 的 `skills/integrations/*/SKILL.md`、HolmesGPT 0.26 起废弃旧 runbook 改
SKILL.md 目录自动发现）都收敛到这个形态，原因是：

- **渐进披露**：交互聊天只注入一行"索引"（name + description），Agent 认为需要时才 `load_skill` 拉全文
  —— 省 token，且不污染主提示词；
- **可热更新**：技能是数据不是代码，改完即生效（`invoke` 时重扫盘/读库）；
- **可移植**：买家加自己团队的排障手册，不用改平台代码。

## 2. SKILL.md 规范

```markdown
---
name: disk-troubleshoot          # 必填；缺省用目录名
description: 磁盘问题专项：区分空间不足与 inode 不足…   # 必填，缺失即失配（强校验）
alerts: [DiskFull, DiskHigh]     # 可选：按告警名 scope
rca_priority: 5                  # 越小越先加载（内置核心=1，领域=5）
---

## 何时用
## 动作（步骤）
## 边界（这个版本做不到什么）
```

规则（都是踩过的）：
- `description` 决定"什么时候被匹配到"，写成"做什么 + 什么场景用"，别写成标题；
- 正文只写**当前工具面能做到**的动作。写一个这个版本没有的能力（比如 `jq` 解析落盘文件、
  远程读日志），模型会照着试然后失败——**这是幻觉的主要来源之一**；
- 边界段必须写实（"远程主机不可得 → 在 not_checked 里说明"）。

## 3. 连接检查（fail-closed，抄 Aurora）

技能可以声明外部依赖：

```python
"disk-troubleshoot": {
    "description": "...",
    "check": {"requires": ["platform_host"]},   # 需要"平台自身主机已纳管"才能读日志/进程
    "body": "...",
}
```

目前支持的依赖项（`_check_requirements`）：

| requires | 判定 | 常见于 |
|---|---|---|
| `hosts` | 至少纳管 1 台主机 | 主机类技能 |
| `metrics` | 近 5 分钟有主机上报 | 指标类技能 |
| `probes` | 至少 1 条探活配置 | 探活类技能 |
| `cases` | 案例库非空 | 案例检索类技能 |
| `platform_host` | 存在平台自身主机（可读日志/进程） | 日志/进程/磁盘取证 |

**语义（关键）**：检查**明确失败** → 该技能**不进索引、也不可加载**（`load_skill` 返回空，
等于"技能不存在"）。这样模型不会去加载一个用不了的工具/流程。
检查结果为"未检查"（从没跑过）→ **默认放行**，否则没初始化就把技能全禁了。

检查入口：
```bash
POST /api/ops/skills/{id}/check      # UI：技能管理页「连接检查」按钮
```
另有后台任务**每 30 分钟自动重跑**领域技能的连接检查（环境变了自动跟上）。

## 4. 内置技能清单（3 核心 + 5 领域）

| 技能 | 定位 | 依赖 |
|---|---|---|
| `core-investigation` | 调查方法论（假设驱动/证伪优先） | 无（恒加载） |
| `core-safety` | 只读优先与变更纪律 | 无 |
| `core-reporting` | 报告写作规范（诚实标不确定性） | 无 |
| `host-health-diagnose` | 主机健康度（CPU/内存/磁盘/负载分层判类） | hosts |
| `metric-analysis` | 指标窗口对比（阶跃/尖峰/单调增长） | metrics |
| `log-search` | 日志取证（含"读不到就给可复制命令"） | platform_host |
| `case-recall` | 历史案例当假设来源（不是结论） | cases |
| `disk-troubleshoot` | 磁盘专项（增速估打满时间） | platform_host |

## 5. 手把手：写一个"证书到期处置"技能

```markdown
<!-- backend/skills/cert-renew/SKILL.md -->
---
name: cert-renew
description: HTTPS 证书临期处置：确认到期时间、影响面与续签路径，给出可验证的续签与验证步骤。
rca_priority: 6
---

## 何时用
证书剩余天数告警（探活类型 https-cert 的 last_latency_ms < 30）。

## 动作
1. `check_probe` 确认是哪几个探活的证书临期，读回剩余天数（这个取值是**天数**，不是延迟）。
2. `host_info` 看该主机还有哪些服务，评估影响面（哪些域名共用证书）。
3. 平台自身主机可 `read_log_tail` 看 ACME/nginx 续签日志；远程主机给命令：
   `openssl s_client -connect <host>:443 -servername <domain> </dev/null 2>/dev/null | openssl x509 -noout -dates`

## 边界
V1 不代执行续签；证书剩余天数是 Agent 侧 TLS 握手探测得到的，不含链上中间证书的独立到期时间。
```

导入与检查：

```bash
# 1) 放到 backend/skills/<名字>/SKILL.md（目录扫描 max_depth=2）
# 2) 平台导入（幂等）
POST /api/ops/skills/import
# 3) 跑连接检查确认可用
POST /api/ops/skills/{id}/check
```

也可以走 UI：「技能管理 → 扫描 skills 目录导入 / 新建技能」。

## 6. 调试技能是否被加载

1. `GET /api/ops/skills` → 看 `connection_check.ok` 与 `requires`；
2. 诊断时 SSE 里的 `tool_call: load_skill {name: ...}` 说明模型确实加载了它；
3. `engine-state` 与诊断报告里的 `tools_used` 能印证；
4. 索引不进 prompt 时，先看是不是连接检查失败被 fail-closed 挡了（这是最常见的"技能不生效"原因）。

## 7. 设计边界

- 技能是**指引（DIRECTIONS）不是结论（RESULTS）**：`load_skill` 返回时会包一层
  `<skill>` 标签并明确提示"要以 ✅/❌ 清单 + 根因 + 修复格式汇报"；
- V1 不做技能市场、不做 Git 同步、不做沙箱（调研明确列为砍掉项）；
- 技能的 `tools` 字段目前是展示用元数据，**不做硬约束**——真正的约束是全局只读工具面。
