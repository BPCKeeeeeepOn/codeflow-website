# 教程 08 · 处置闭环与四层护栏

> 目标：讲清 Runbook 五段怎么生成、护栏四层怎么判定、**为什么 V1 不代执行命令**，
> 以及白名单/HITL/审计三者怎么配合。
> 代码：`app/services/runbook.py`（护栏 + fixcheck + 变更单）、`app/routers/runbooks.py`。

## 1. 全链路

```
诊断报告(## VALIDATED FIXES)
   └─ fixcheck：每条建议必须匹配预置"验证对"（VERIFY_PAIRS）才进变更单
        ├─ 匹配 + 像动作 → VALIDATED（带 evidence_ref / 影响 / 风险 / 回滚）
        └─ 不匹配 / 像事实陈述 → UNVALIDATED（不进变更单）
   └─ 生成 Runbook（五段：风险评估 / 前置检查 / 执行步骤 / 回滚预案 / 验证口径）
        └─ 每次修改 copy-on-write 出 v2、v3…（旧版只读，历史可回看）
   └─ 执行单步 → 四层护栏 → 放行则返回"待执行命令" + 写 action_audit
```

## 2. 五层护栏（顺序固定）

| 层 | 判定 | 结果 |
|---|---|---|
| ① denylist | 命中危险模式（`rm -rf /`、`mkfs`、`dd if=`写盘、`shutdown/reboot`、`curl|sh`、`drop database` …） | **拒绝** + 审计 |
| ② 只读前缀白名单 | 命令前缀在只读集合（`df`、`du`、`free`、`ps`、`iostat`、`systemctl status` …） | **放行**（`approval_mode=readonly`，无需确认） |
| ③ 「仅建议」模式 | `execution_mode=suggest` | **拒绝**（平台只给建议，不出执行指令） |
| ④ 「白名单自动」+ 命中动作清单 | `execution_mode=auto` 且命令命中 `action_allowlist` | 放行（`approval_mode=auto`，记 `approved_by`） |
| ⑤ 人工确认 | 其余所有非只读步骤 | 必须出示一次性 `confirm_token`（`approval_mode=manual`），否则 403 `HITL_REQUIRED` |

### 2.1 三种执行模式（FR-E2 的"三选"）

| 模式 | 语义 | 典型场景 |
|---|---|---|
| `suggest` 仅建议 | 平台只展示建议命令，**不生成执行指令** | 生产上严格"只给方案不碰机器" |
| `manual` 人工确认（默认） | 非只读步骤需过一次确认卡 → 签票 → 执行 | 单人自用：让审计能证明"看过风险才点的" |
| `auto` 白名单自动 | **仅命中动作清单**的动作免确认，其余仍需确认 | 例行动作（清理临时文件、重启 nginx）不想每次点 |

切换：变更单详情底部下拉（admin）。老字段 `whitelist_enabled` 保留为同步列（`= auto`），老客户端不受影响。

### 2.2 审批凭据（为什么 `approved=true` 不可信）

旧实现里放行依据是客户端自报的 `approved: true` —— 谁都能 `curl` 直接发过来，
`action_audit` 里那句"已放行"证明不了有人审过。现在改成**凭据制**：

```
POST /ops/runbooks/{rid}/steps/{idx}/confirm   # 签发：落操作者/时间/IP/命令快照，返回 cfm-<32hex>
POST /ops/runbooks/{rid}/execute {step_idx, confirm_token}   # 校验：未用 + 未过期(300s) + 同一 runbook/step
```
token 只存 **sha256 哈希**，用后即焚（重放被拒）。审计表新增 `approval_mode / approved_by / approved_at`，
`GET /ops/action-audit` 能看到"谁在何时以何种方式批准了哪一步"。这也是 V2 远程执行通道的直接地基。

### 2.3 动作清单（脚本级白名单）

```bash
GET /api/ops/action-allowlist      # 内置：cleanup-tmp / restart-nginx / restart-redis / logrotate / …
# 自定义：环境变量 ACTION_ALLOWLIST="my-job=^systemctl restart my-app$;cleanup=^find /var/tmp .*-delete$"
```
关键语义：**"白名单自动"只覆盖清单里的动作**；没命中的动作即使在 auto 模式下也要人工确认
（避免"开了自动就等于全部自动"）。

denylist 是**大小写不敏感**的前缀/子串匹配（`DENYLIST_PATTERNS`），
只读白名单是**前缀**匹配（`READONLY_PREFIXES`）。每一次判定（含被拒）都写 `action_audit`
（`operator=ai|user`、`params`、`guardrail_verdict`、`result`）。

> ⚠️ **V1 的语义边界（务必对客户讲清楚）**：平台**不在目标机上执行命令**。
> "执行"这一步的实际行为是：判定 → 审计 → 返回一条**可复制的命令**给运维，由人执行。
> 因此"执行期间挂巡检护栏、异常即中止"这个场景在 V1 不成立（没有真正在跑的命令可以中止），
> 已明确列为 V2（远程执行通道）。演示时不要说成"平台会自动重启服务"。

## 3. fixcheck：为什么"建议"要过验证对

`fixcheck_findings()` 只从**显式建议段**（`## VALIDATED FIXES`，兼容 `## Recommended fix` 等旧名）
抽取条目，**不做 Summary 兜底**。原因（D7 实测教训）：早期没有建议段时会退化成从 Summary
抓项目符号，结果把"故障事实（可证实）：8080 端口无进程"这类**事实陈述**当成修复动作去匹配，
产出看似合规、内容无意义的变更单 —— 违背 FR-D6"没验证过的修复不建议"的本意。

判定两条：
- 命中 `VERIFY_PAIRS` 里某个验证对（如"重启服务" ↔ `systemctl status <svc>` 前置确认）；
- 且句子**像动作**（动作词出现在句中即可，不要求动词开头——“若确认…则重启服务”也是建议）。

不满足的进 `UNVALIDATED（不进变更单）` 段，方便人一眼看出"这条为什么没进单"。

## 4. 变更单五段与版本化

| 段 | 内容 | 来源 |
|---|---|---|
| 风险评估 | `risk_level`（low/mid/high）+ 说明 | 按动作类型映射（`_risk_for`） |
| 前置检查 | 执行前确认项（`pre_checks`） | 验证对里的 `check` 命令 |
| 执行步骤 | `steps[]`，每步带 `mode`：`readonly` / `approval` | 建议条目 |
| 回滚预案 | 每类动作的回滚方式 | `_rollback_for` |
| 验证口径 | 执行后怎么确认有效 | 验证对 |

**版本化是 copy-on-write**：每次改单写入 `runbook_versions` 的**全量快照**（不是 diff），
旧版只读。好处是"回看历史"永远精确、不依赖 diff 重放；代价是存储大一些（变更单体量很小，可接受）。

## 5. 案例沉淀（闭环的最后一环）

事件关闭时自动写 `case_cards`（现象 / 根因 / 处置摘要 + **embedding**），
下次诊断时 `search_cases` 向量召回注入上下文。两个细节：

- **SeekDB 向量召回是标准路径**（`l2_distance`），embedding 不可用时降级为文本匹配，
  并在返回值里如实标注 `mode`；
- 向量失败只**冷却 5 分钟**再重试（不是一票否决），否则一次网络抖动就会让这个进程
  此后所有案例都不带向量、召回全走文本（D8 实测修过）。

## 6. 操作演示：从报告到变更单

```bash
# 1) 确保事件有报告（先跑一次诊断）
POST /api/ops/incidents/{id}/diagnose
# 2) 生成变更单（只取 VALIDATED FIXES；无建议段会明确报错而不是凑数）
POST /api/ops/runbooks/generate/{incident_id}
# 3) 只读步骤：直接放行（无需确认）
POST /api/ops/runbooks/{rid}/execute  {"step_idx": 0}
# 3b) 变更步骤：先取一次性确认凭据（确认卡的数据来源）
POST /api/ops/runbooks/{rid}/steps/1/confirm        → {confirm_token, allowlisted, cmd, risk_level, rollback}
# 3c) 带票执行（不带票 → 403 HITL_REQUIRED；票只能用一次且 300s 过期）
POST /api/ops/runbooks/{rid}/execute  {"step_idx": 1, "confirm_token": "<cfm-...>"}
# 4) 试一个危险命令（应被 denylist 拒绝并留审计）
POST /api/ops/runbooks/{rid}/execute  {"step_idx": 2, "confirm_token": "<cfm-...>"}
# 5) 全局处置审计（跨变更单查询）
GET /api/ops/action-audit?host_ident=<ident>&operator=user&page=1
```

## 7. 已知取舍（诚实清单）

| 项 | 现状 | 说明 |
|---|---|---|
| 命令执行 | **不代执行** | 只判定+审计+给命令；V2 做远程通道（含审批流） |
| 执行中中止（巡检护栏） | 未实现 | 依赖远程通道；V2 |
| "三模式"配置 | ✅ 已落地 | `execution_mode`（suggest/manual/auto）+ 动作清单，见 §2.1/§2.3 |
| 脚本级白名单 | 前缀级 | 不是"整脚本哈希白名单"；V2 可加 |
| 前端"执行"按钮 | ✅ 已改为确认卡 | 非只读步骤先弹确认卡（动作/命令原文/风险/回滚/是否命中清单）→ 确认后带票执行 |
